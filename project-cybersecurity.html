Integrated Ethical Phishing Attack & Cyber Defense Evaluation System

The problem

Phishing simulation and defensive monitoring are often treated as separate exercises.

The project report identifies a visibility gap: phishing-awareness exercises can measure how users react, while server, network, and SIEM tools separately collect technical evidence. When those activities are isolated, it is difficult to trace a suspicious interaction from the simulated event through the generated web and network logs and into the defensive monitoring workflow.

The project therefore explored a unified lab where controlled phishing activity could be observed through Apache logs, centrally collected in Splunk, transformed into structured fields, queried with SPL, visualized in dashboards, and compared with network observations from Ettercap.

Project objectives

Evaluate the complete path from controlled activity to defensive evidence.

Centralize evidence

Bring phishing-related web and system events into Splunk rather than inspecting separate logs manually.

Structure raw logs

Turn Apache access events into useful fields that can support filtering, reporting, and investigation.

Analyze suspicious patterns

Use SPL searches and visualizations to study HTTP activity and other indicators in the controlled environment.

Add network context

Use Ettercap observations to compare host and connection behaviour with the application-level evidence seen in Splunk.

System design

A multi-layer lab links controlled phishing activity, web-server evidence, SIEM analytics, and network observation.

The report's architecture combines an ethical phishing layer with log collection and forwarding, Splunk-based indexing and monitoring, dashboards, and supporting security tools. Apache provides web-access evidence, the Universal Forwarder transports server logs, Splunk performs indexing and analysis, and Ettercap contributes network-level visibility.

Implementation

The useful engineering work is in making the evidence pipeline function end to end.

01

Virtualized lab and network preparation

Ubuntu and Kali Linux systems were used in an isolated environment. The report documents static addressing, connectivity checks, and separate systems for the Splunk server and Apache server so data could move predictably through the lab.

02

Apache and Splunk service setup

Apache generated web-access events while Splunk Enterprise provided the central search and analysis platform. A dedicated non-root Splunk service account was used rather than running the service as root.

03

Universal Forwarder pipeline

A dedicated web index and apache_access source type were configured. The Forwarder monitored Apache's access log and transmitted the events to Splunk through the configured receiving pipeline, followed by service restart and ingestion verification.

04

Permissions and operational debugging

The Splunk service initially needed permission to read the Apache log owned by root:adm. The report documents resolving that dependency so the Forwarder could continuously monitor the source file.

05

Custom Regex field extraction

Raw Apache events were not sufficient for structured reporting. After Splunk's automatically generated extraction was inaccurate, a custom regular expression was refined to expose fields including client IP, timestamp, method, URI, status code, request size, referrer, and user agent.

06

SPL search and visualization

The extracted fields were then used with Splunk Search Processing Language for filtering, field-based analysis, deduplication where needed, tabular views, top-value analysis, and visual summaries.

07

Network observation with Ettercap

Ettercap supplied a second source of defensive evidence by showing hosts, connections, plugin-based indicators, and abnormal communication patterns inside the controlled test network.

Results

A working evidence chain was demonstrated from web activity to centralized analysis.

A

Apache events reached Splunk

The report verifies successful ingestion into the configured web index with the apache_access source type.

B

Raw data became structured

The custom extraction exposed meaningful HTTP fields, allowing field-aware searches and report generation instead of treating Splunk as only a raw-text search engine.

C

SPL supported investigation

Searches, filtering, statistics, deduplication, tables, and visualizations were used to make suspicious access behaviour easier to interpret.

D

Network observations complemented SIEM data

Ettercap's host and connection views added contextual evidence around traffic generated inside the controlled environment.

The report demonstrates functionality and an end-to-end lab workflow. It does not provide independently validated production benchmarks, a measured enterprise-scale detection rate, or evidence of commercial deployment, so this case study does not claim those outcomes.

Engineering learnings

The project is strongest as a log-engineering and security-observability case study.

01 · Collection is only the first step

Receiving events in a SIEM does not automatically make them useful. Correct source typing and field extraction determine whether analysts can query and report on the data effectively.

02 · Permissions are part of the data pipeline

A perfectly configured forwarder still fails if its service account cannot read the source logs. Operational Linux configuration was therefore part of the engineering problem.

03 · Automatic parsing is not always enough

The report explicitly records that Splunk's automatically generated extraction was inaccurate, leading to a custom Regex solution and verification against the real Apache events.

04 · Multiple evidence sources improve interpretation

Application logs, SIEM searches, dashboards, and network observations each expose different parts of the same controlled event sequence.

Future improvements

Separate demonstrated functionality from the report's proposed next stage.

The report proposes expanding the project with broader enterprise log sources, stronger real-time notification workflows, automated response integration, user-awareness modules, machine-learning-based anomaly detection, and cloud deployment. These are future directions, not features presented here as already implemented.
