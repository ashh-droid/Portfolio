The problem

Choose feasible deliveries when demand exceeds fleet capacity.

Not every order can be allocated when vehicles have limited remaining capacity. A useful dispatch plan must prioritize important orders, choose a suitable vehicle, avoid exceeding capacity and make unassigned deliveries visible rather than hiding them.

Routing choices

Separate which orders are assigned from how each vehicle visits its stops.

01

Priority-first allocation

Orders are considered HIGH, MEDIUM then LOW, with heavier orders first within each tier. The algorithm selects the nearest feasible vehicle using Haversine great-circle distance and deterministic tie-breaking.

02

Capacity rules

Each assignment reduces its vehicle's available capacity. Unassigned orders report whether no vehicle is available, the order exceeds maximum single-vehicle capacity or the fleet lacks remaining space.

03

Optional distance-aware strategy

A bounded 2-opt pass reorders stops within allocated vehicle routes when that shortens the route. It preserves the assigned-order sets and loads; it is a local heuristic rather than a global route optimizer.

Reliability and tests

Exercise both the HTTP contract and the planning invariants.

JUnit and Spring integration tests cover the sample dataset, invalid input, CRUD behavior, capacity constraints and both dispatch strategies. Seeded randomized cases check allocation invariants, and a 200-stop test exercises the distance-aware route improvement. GitHub Actions runs the Java build, tests and configured JaCoCo coverage checks.

Deployment and limits

A verifiable API demo, not a production logistics platform.

The Dockerized Spring Boot service is deployed on Render with a restartable H2 demonstration database and optional synthetic-data seeding. Haversine estimates great-circle distance rather than road distance, and the heuristics are not guaranteed to find the globally shortest routes. The demo exposes unauthenticated write APIs and should not store real customer data without access controls.
