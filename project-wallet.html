The problem

Model balance-changing operations without leaving partial updates behind.

A wallet transfer changes more than one row: the sender balance decreases, the recipient balance increases, and a transaction record is created. The backend needs to validate the request, authorize the caller, persist all related changes together, and return consistent API errors when something fails.

Architecture

Separate HTTP handling, business rules, and persistence through a layered Spring Boot design.

01

Controller layer

REST controllers receive requests and expose authentication, wallet, transfer, history, and admin endpoints.

02

Service layer

Business rules such as self-transfer checks, balance validation, deposits, transfers, and transaction mapping stay outside the controller.

03

Repository layer

Spring Data JPA repositories manage wallet, user, and transaction persistence through Hibernate and PostgreSQL.

Authentication & authorization

Protect wallet operations with stateless JWT authentication and role-aware access.

JWT authentication

Registration and login issue JWTs that are processed by Spring Security for protected API requests.

USER / ADMIN roles

Wallet routes require authenticated access, while administration endpoints are restricted to the ADMIN role.

Password handling

Passwords are stored as BCrypt hashes, while JWT and database secrets are externalized from source control.

Transactional consistency

Use one database transaction for the complete transfer operation.

The transfer service is annotated with @Transactional. If validation or persistence fails before completion, Spring rolls the transaction back instead of leaving only one balance updated.

01

BigDecimal for money

Wallet balances and transfer amounts use BigDecimal so decimal monetary values are not handled with binary floating-point arithmetic.

02

Optimistic locking

The Wallet entity uses @Version so concurrent updates can be detected instead of silently overwriting a newer wallet state.

03

Atomic business operation

Debit, credit, and transaction-record creation belong to the same transaction boundary and commit together.

API correctness

Keep request validation, error responses, and transaction history predictable.

Validation

Requests validate transfer amounts, users, available balance, self-transfers, and authenticated identity before changing state.

Centralized exceptions

A global exception handler turns application errors into a consistent API response structure rather than exposing stack traces.

Paginated history

Transaction history uses Spring Data pagination so clients can request pages instead of loading all records at once.

The project is packaged with Docker and Docker Compose, with PostgreSQL data stored in a persistent Docker volume.

What I would improve next

Make the demo backend easier to evolve and operate under real production conditions.

The repository identifies Flyway migrations, OpenAPI documentation, broader integration testing, explicit optimistic-lock conflict handling, refresh tokens, rate limiting, audit logging, and CI as logical next improvements. The current project remains a portfolio wallet simulation and does not process real money or connect to banking networks.
